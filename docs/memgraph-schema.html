Factory graph in Memgraph

Every entity of one force, and every engine-verified connection between them, exported from the live save and loaded into Memgraph for Cypher queries.

status implemented engine Factorio 2.0.77 store Memgraph 3.14 (MAGE) + Lab command factorio-ai-player graph

1 · Quick start

just graph-up        # Memgraph on bolt://127.0.0.1:7687, Lab on http://127.0.0.1:3000
just graph-sync      # pause for game reads, then write, load, and resume the game
just graph-shell     # mgconsole inside the container

Exports do not change game entities, but briefly pause the shared save by default for all game reads. The prior pause state is restored on success, error or cancellation before snapshot disk writes and Memgraph loading; an already paused game stays paused. graph sync then clears any pause lease and resumes the simulation, so it always ends with the game running. Use just graph-sync --pause=false or just graph-export --pause=false to leave pause state untouched during the reads. Snapshots land in .factorio/graph/snap-* (newest five kept, LATEST names the newest); just graph-load --in DIR loads any of them again without touching the game's pause state.

2 · Pipeline

  1. Pause guard. Unless --pause=false or mutation input pause:false is supplied, remember the prior game pause state and pause the shared save before any export reads.
  2. Census before. One call totals each surface for the force: static entities (exported by leaves), mobile entities (characters, cars, spidertrons, rolling stock) and skipped ones (robots and transient effects such as projectiles and fire).
  3. Chunk census. Generated chunks are visited in pages of 20,000 and every chunk intersecting an entity of the force is kept with its count.
  4. Leaf plan. Non-empty chunks are grouped into aligned 256-tile cells and each cell is split into quadrants until its estimated count fits --leaf-max (default 2000) or it is a single chunk. Leaves never overlap and cover every non-empty chunk.
  5. Leaf reads. One RCON call per leaf, up to --concurrency (default 4) in parallel. A leaf owns every static entity whose centre lies in its half-open rectangle [lx,rx)×[ly,ry), so each entity is owned exactly once; the scan is padded by 3 tiles so arms and drills at the border still resolve their targets. A leaf that fails on transport is split into quadrants and retried.
  6. Mobile read. One call per surface reads every mobile entity in a single tick, so moving vehicles are neither missed nor counted twice.
  7. Census after and reconciliation (§6), then the builder routes raw engine links into relationship types (§4) and reads production catalogs. After the final game read, the prior pause state is restored before writing the snapshot directory atomically; error and cancellation paths also restore it. An already paused game remains paused.
  8. Load. Schema applied, nodes and edges MERGEd in batches, then everything in the snapshot's scopes that does not carry its id is deleted.

Entity properties: id, unit, name, type, surface, force, x, y, direction, quality, status (engine status name), recipe, recipeQuality, recipeSource (previous for an idle furnace), modules (name:quality:count strings), electricNetwork, logisticNetwork, train, mobile, tick (the tick of the read that owned it), snapshot, scope. Fluid-bearing entities also carry fluids (index|name|amount|temperature per non-empty fluidbox), fluidTotal and fluidCapacity; ghost buildings carry ghostRecipe; requester and buffer chests carry requests; roboports carry robots.

Crafting counters (assembling-machine, furnace, rocket-silo): productsFinished (cumulative crafts since build), craftingProgress (0–1 of the current craft), craftingSpeed (the machine's current speed after module and beacon effects, so 60 × craftingSpeed / recipe.energy is the real rate) and on furnaces previousRecipe — when it differs from recipe the furnace has switched recipes, which is how a drill over two ores makes one furnace emit two products.

Drills carry areaResources and areaAmounts (sorted name:tiles / name:amount over the whole mining_area), areaTiles, and the area corners miningLeft, miningTop, miningRight, miningBottom. MINES still points at the single current mining_target, so a drill whose areaResources has two entries is the one that mixes ores.

Inserters carry pickupX/pickupY, dropX/dropY, pickupLeftLane/pickupRightLane, useFilters, filterMode, filters ({index,name,quality}), stackSizeOverride, held (name:count in the hand), and dropResolved:false when the drop tile holds no entity (an arm pointing at nothing, not an export bug).

Belt lanes. Every belt-family node (transport, underground, splitter, loader, linked) samples all engine transport lines: lanes holds one index|lineName|side|item:count+… string per non-empty line, left/right stay lines 1 and 2 (line 1 is left_line), while leftCount/rightCount sum every line of that side — a splitter keeps items on lines 5–8 and an underground on 3–4, so counting lines 1–2 alone would report zero. mixedLeft/mixedRight are true when a side holds more than one item or quality anywhere on that entity. Line names are pinned per index (1 left_line, 2 right_line, 3 left_underground_line, 4 right_underground_line, 5 left_split_line, 6 right_split_line, 7 secondary_left_split_line, 8 secondary_right_split_line) and match beltTiles/beltStretch, because defines.transport_line collides on 3/4 and 7/8 and an index-built table would rename lanes between loads.

Belt stretches. :BeltStretch {id} is one sequential run: every belt outputs into the next, underground and linked pairs are followed, curves continue, and a splitter always ends the run — each splitter output starts a new one. A side-load ends the loading run and joins it to the main run. Properties: belts, undergrounds, headUnit/headX/headY, tailUnit/tailX/tailY, endKind (splitter · sideload · deadend · loader · loop), per-item lists itemsLeft/itemsRight (name:count strings, e.g. iron-gear-wheel:87), leftCount/rightCount, mixedLeft/mixedRight. Id is surface:stretch:<head unit> (a headless loop uses its smallest unit), so it is stable while that head belt exists.

Production graph. :Item {id} (surface:item:name) exists once per item or fluid a snapshot references, with name and kind (item · fluid); quality is never a separate node, it lives on the edge. :Recipe {id} (surface:recipe:name) carries energy (craft seconds at speed 1) and category. Both are derived, per surface, and pruned with the scope they belong to. Entities reach items through RUNS (machine → recipe), PRODUCES/CONSUMES (recipe → item per craft, entity → item per minute), BURNS (fuel), CONTAINS (chest stock) and HOLDS (machine input/output/fuel slots). Rates are nameplates: perMinute = 60 × craftingSpeed / recipe.energy × amount, ignoring modules, beacons and productivity modules; a drill adds miningTime and the force's mining productivity bonus. CONTAINS and HOLDS are frozen at the leaf tick like belt lanes — a sample, not live stock. Infinity containers report their filters and contents; linked-container contents are not exported.

Identity. id = surface:unit_number, else surface:type:name:x:y (resources have no unit number). Unit numbers are global, the surface prefix keeps ids readable and linked belts across surfaces distinct.

Network nodes. :Network:ElectricNetwork (surface:electric:N), :Network:LogisticNetwork (surface:force:logistic:N), :Network:CircuitNetwork (surface:circuit:N, with color).

Sequence splitters. A splitter (or lane-splitter) is a :Belt and a :Splitter with inputPriority/outputPriority (none, left, right) and filters ({index: 1, name, quality}) read from the engine's single splitter_filter property — not from get_filter(slot), which does not apply to splitters in 2.0.77. Its two outputs are separate edges with fromPort = left or right, resolved geometrically from the two bounding boxes and the splitter's direction — the side counter-clockwise of travel, so an eastward splitter's north output is left. An edge entering the splitter carries toPort. Neither engine source names the side: belt_neighbours keys are ordering only, and the transport-line names left_split_line/right_split_line are the two lanes of one output belt while secondary_*_split_line names the second output — measured on a connected splitter. Both neighbouring belts report the same link back without a port, and the loader merges the port onto the single edge instead of creating a second. When the geometry cannot resolve (fromPort/toPort absent) the raw neighbour key is kept separately as fromPortIndex/toPortIndex, so fromPort only ever holds left or right.

Every relationship carries key, snapshot and scope. Connector names follow the owner (pole_copper vs power_switch_left_copper share id 5; combinators use combinator_input_*/combinator_output_*).

Kind routing is strict. Raw links arrive per owning entity with a kind; the exporter routes each kind to one relationship type and fails on an unknown kind rather than dropping connectivity. Pickups arrive as source→arm and are re-hung on the arm. Fluid ports, wires and rails are reported from both ends; they fold into one edge on the sorted endpoint pair. dirA/dirB are the raw per-port declarations and never imply a direction of flow.

5 · Coverage

Captured

  • Every static entity of the force on every surface it owns entities on, including ghosts, poles, rails, combinators, defenses.
  • Every vehicle, character and piece of rolling stock (one-tick mobile pass).
  • Belt, inserter, drill, beacon, fluid, copper, circuit and rail connections; electric, logistic and circuit network membership.
  • Recipe, modules, status, quality and direction on each node.
  • Production: item and recipe nodes, per-minute nameplate rates for crafters, drills and infinity containers, plus point-in-time CONTAINS/HOLDS/BURNS contents.
  • Fluidbox contents (fluids, fluidTotal, fluidCapacity), vehicle, wagon, turret and lab inventories, roboport robot stock, requester-chest requests, ghost recipes, and each crafting machine's effective craftingSpeed.

Deliberately not captured

  • Robots and transient effects (counted as skipped in the census); roboport coverage cells and logistic-network robot counts stay live reads.
  • Live stock and measured throughput — contents appear only as leaf-tick samples (items, fluids, fuel, input, output, lanes); linked-container contents are not sampled at all.
  • Splitter lane routing (engine-private), heat-pipe connectivity and temperature, heat networks, train schedules and paths, rail block/signal state, combinator parameters and live circuit signal values, electric-network statistics, tiles, trees, enemies.

6 · Completeness

The census counts entities by force and type; leaves own entities by centre. Because leaves partition every non-empty chunk, each static entity is exported exactly once, and the exported count must equal the census. The census is taken before and after the scan:

The default pause prevents normal simulation changes during the scan. With --pause=false or pause:false, the save can advance between reads and produce drift; pausing does not exclude concurrent external edits through other clients.

StatusConditionMeaningExit / load
completebefore = after = exportednothing changed during the scan and nothing was missed0 / loads
driftbefore ≠ afterbots or players built or removed entities while the scan ran; each node is correct at its own tick0 / loads; rerun for an exact snapshot
incompletebefore = after ≠ exporteda hole: something counted was not exportednon-zero / refused unless --allow-incomplete

An entity owned by two leaves is an error, not a merge. The manifest records every leaf's area, tick, owned count, edge count and duration.

7 · Snapshots and loading

A snapshot directory holds nodes.jsonl ({id, labels, props}), edges.jsonl ({type, from, fromLabel, to, toLabel, key, props}) and manifest.json. It is written to a temp directory and renamed into place, so a reader never sees half a snapshot.

Loading MERGEs nodes by id and relationships by key, so loading the same snapshot twice is a no-op. A snapshot covers one scope per surface (surface|force); after all rows are written, every node, network and relationship in those scopes that does not carry the new snapshot id is deleted. A snapshot replaces its scopes and never patches them, because the world it describes may have been rebuilt in between. (:Snapshot {loaded}) flips to true only after pruning.

Labels and relationship types are spliced into Cypher from fixed allow-lists; anything else is rejected before a query is built.

Schema

memgraph/schema.cypherl holds unique constraints on :Entity(id), :Network(id), :Snapshot(id), the matching label-property indexes (Memgraph does not index a constraint by itself), scope indexes for pruning, and indexes on unit, name, type, status, :Machine(recipe) and the main labels. The container runs it with --init-file on every start and graph load reapplies it; re-creating an existing index or constraint is a no-op. One statement per line, no comments: the init file is parsed line by line.

Leaf and mobile reads run the topology prelude plus the graph prelude. The navigation mod compiles both once and exposes graph_leaf and graph_mobile on factorio_ai_topology, so the console sends only a remote.call. A save whose loaded mod predates those ops gets the same Lua inline. That path is correct but slow for a reason unrelated to Lua: in-game load() of the 25 KB prelude takes 1.8 ms, yet the console command takes ~1.2 s, and the delay scales with the command's entropy (24 KB of repeated text: 4 ms; 24 KB of random text: 2.9 s). A multiplayer server replicates each console command to its clients, so large commands cost transmission time. Restarting Factorio loads the new ops.

Each leaf read runs on the game thread for its duration; --leaf-max trades the number of calls against the length of each stall.

9 · Query cookbook

Through GraphQL, query { memgraph { schema { labels { name nodes properties { name count } } relationships { name edges properties { name count } } snapshot { id status nodes edges } } } returns the labels, relationship types, property keys and latest loaded snapshot without writing Cypher. It is derived from loaded data, so a label, type or property that was never loaded is absent, and declared indexes/constraints remain in memgraph/schema.cypherl.

Mine → belt run → inserter → smelter

MATCH p = (d:MiningDrill)-[:DROPS_ON]->(:Belt)-[:BELT_OUT*0..300]->(b:Belt)
          <-[:PICKS_FROM]-(i:Inserter)-[:DROPS_TO]->(m:Machine)
MATCH (d)-[:MINES]->(ore:ResourceTile)
RETURN ore.name, d.id, i.id, m.name, m.recipe, length(p) AS hops;

Everything feeding one machine

MATCH (m:Machine {unit: $unit})<-[:DROPS_TO]-(i:Inserter)-[:PICKS_FROM]->(src)
OPTIONAL MATCH (up:Belt)-[:BELT_OUT*1..300]->(src)
OPTIONAL MATCH (up)<-[:DROPS_ON|DROPS_TO]-(feeder)
RETURN i.status, src.name, collect(DISTINCT feeder.name) AS feeders;

Everything that puts items into a belt stretch (including upstream runs)

MATCH (:Belt {unit: 815})-[:IN_STRETCH]->(s:BeltStretch)
MATCH (up:BeltStretch)-[:FLOWS_INTO*0..100]->(s)
MATCH (x)-[f:FEEDS_STRETCH]->(up) WHERE NOT x:Splitter AND f.via IS NULL
OPTIONAL MATCH (x:Inserter)-[:PICKS_FROM]->(src)
RETURN DISTINCT labels(x), x.name, x.unit, src.name, src.unit, src.recipe, up.id;

Where a machine's output goes

MATCH (m:Machine {unit: $u})<-[:PICKS_FROM]-(i:Inserter)-[:FEEDS_STRETCH]->(s)
MATCH (s)-[:FLOWS_INTO*0..100]->(d)<-[:TAKES_FROM_STRETCH]-(t:Inserter)-[:DROPS_TO]->(c)
RETURN DISTINCT c.name, c.unit, c.recipe;

Drills that mine more than one ore, and mixed lanes

MATCH (d:MiningDrill) WHERE size(d.areaResources) > 1
MATCH (d)-[:DROPS_ON]->(t) RETURN d.unit, d.x, d.y, d.areaResources, t.unit, t.name, t.recipe;

MATCH (b:Belt) WHERE b.mixedLeft OR b.mixedRight
RETURN b.unit, b.type, b.x, b.y, b.lanes ORDER BY b.unit;

Belt heads nothing feeds

MATCH (b:Belt)
WHERE NOT ()-[:BELT_OUT]->(b) AND NOT ()-[:DROPS_ON]->(b) AND NOT ()-[:DROPS_TO]->(b)
RETURN b.id, b.x, b.y;

Splitter outputs and dead sides

MATCH (s:Splitter)-[r:BELT_OUT]->(b:Belt)
WITH s, r.fromPort AS port, b, size([(b)-[:BELT_OUT]->() | 1]) AS downstream
RETURN s.id, s.x, s.y, s.outputPriority, port, b.id,
       CASE WHEN downstream = 0 THEN 'dead side' ELSE 'flows' END;

Inserters bridging belt to belt (candidate defects)

MATCH (a:Belt)<-[:PICKS_FROM]-(i:Inserter)-[:DROPS_TO]->(b:Belt) RETURN i.id, i.x, i.y;

Burner machines with no fuel anywhere upstream (point-in-time contents)

Nodes carry a contents sample taken at the leaf tick: fuel, input, output (furnaces, assemblers, rocket silos, burner drills/boilers/inserters, labs), items (chests, cargo wagons, car and spider trunks), ammo (turrets), robots (roboports), fluids (index|name|amount|temperature per non-empty fluidbox plus fluidTotal/fluidCapacity, so tanks, pipes, fluid wagons and machine boxes are sampled) and left / right (engine transport lines 1 and 2 of any belt-family entity) and left / right (engine transport lines 1 and 2 of any belt-family entity), lanes (index|lineName|side|items for every non-empty line, including underground tunnel and splitter lines) and mixedLeft/mixedRight, each a sorted list of name:count (name@quality:count when not normal). Each list has a matching …Count, present whenever the entity has that inventory, so fuelCount = 0 (burner, empty) differs from no fuelCount (no fuel inventory); the list itself is absent when empty. PICKS_FROM.side is the side of the belt (relative to travel) the inserter stands on; DROPS_TO.side is the lane the dropped item lands on. Contents are volatile: compare against tick and re-export before trusting them.

MATCH (m:Machine) WHERE m.fuelCount = 0
  AND NOT EXISTS { MATCH (m)<-[:DROPS_TO]-(:Inserter)-[:PICKS_FROM]->(b:Belt)
                   WHERE any(x IN coalesce(b.left,[]) + coalesce(b.right,[]) WHERE x STARTS WITH 'coal') }
RETURN m.unit, m.recipe, m.inputCount;

Machines on no electric network

MATCH (m) WHERE (m:Machine OR m:Inserter OR m:MiningDrill)
  AND m.electricNetwork IS NULL AND NOT m.name STARTS WITH 'burner' AND NOT m.name STARTS WITH 'stone'
RETURN m.name, m.x, m.y, m.status;

Beacon coverage per machine

MATCH (m:Machine) OPTIONAL MATCH (b:Beacon)-[:AFFECTS]->(m)
RETURN m.recipe, m.id, count(b) AS beacons ORDER BY beacons;

Fluid neighbourhood (undirected)

MATCH (n:Entity {unit: $unit})-[r:FLUID_LINK]-(other) RETURN other.name, r.dirA, r.dirB, r.ports;

Latest loaded snapshot

MATCH (s:Snapshot {loaded: true}) RETURN s ORDER BY s.id DESC LIMIT 1;

Who produces an item (any producer, recipe or not)

MATCH (e:Entity)-[p:PRODUCES]->(i:Item {name: "iron-plate"})
RETURN e.name, e.unit, e.x, e.y, e.status, p.via, p.perMinute
ORDER BY p.perMinute DESC;

Supply vs demand per item (nameplate rates)

MATCH (i:Item)
OPTIONAL MATCH ()-[p:PRODUCES]->(i) WHERE p.perMinute IS NOT NULL
WITH i, sum(p.perMinute) AS supply
OPTIONAL MATCH (:Entity)-[q:CONSUMES]->(i)
RETURN i.name, supply, sum(q.perMinute) AS demand
ORDER BY coalesce(demand, 0) - coalesce(supply, 0) DESC;

Recipe input tree of a machine

MATCH (m:Machine {unit: $unit})-[:RUNS]->(r:Recipe)
OPTIONAL MATCH (r)-[c:CONSUMES]->(in:Item)
OPTIONAL MATCH (r)-[p:PRODUCES]->(out:Item)
RETURN r.name, r.energy, collect(DISTINCT in.name + " x" + toString(c.amount)) AS inputs,
       collect(DISTINCT out.name + " x" + toString(p.amount)) AS outputs;

Where an item is stored right now (snapshot sample)

MATCH (c:Chest)-[x:CONTAINS]->(:Item {name: "coal"})
RETURN c.name, c.unit, x.count, x.quality ORDER BY x.count DESC;

Machines holding an item in a slot

MATCH (m)-[h:HOLDS]->(:Item {name: "iron-ore"})
RETURN m.name, m.unit, h.slot, h.count, h.quality;

9b · Typed trace reads (no Cypher)

Each read is a field under memgraph { }, takes a unitNumber (decimal string) and answers summary, then outline, then normalized detail (nodes, paths as node ids), with truncated and snapshot on every result. Edge directions: PICKS_FROM and DROPS_TO both leave the inserter; the reads chain them for you. Named gqlcli ops: supply-chain, downstream-chain, ingredient-coverage, area-graph, memgraph-query, memgraph-schema.

supplyChain: everything upstream of a Machine, Chest or Belt

query { memgraph { supplyChain(input: {unitNumber: "143"}) { summary { pathCount nodeCount } outline origins { id name } truncated } } }

Validated: the outline reads 143 assembling-machine-1 (electronic-circuit) [working] <- arm 239 ... <- 37 infinity-chest [normal]; <- means "is fed by". resolution: STRETCH is compact but coarse; BELT (default) is exact. origins are the roots of the walk (drills, chests, furnaces).

downstreamChain: where a node's output goes

query { memgraph { downstreamChain(input: {unitNumber: "391"}) { outline sinks { id name } truncated } } }

Validated: belt 391 → arm 390 → 370 assembling-machine-1 → arm 435 → 436 infinity-chest. -> means "feeds"; attention flags sink:belt, a line nothing picks from. BELT resolution only.

ingredientCoverage: does every recipe ingredient have a feeding inserter

query { memgraph { ingredientCoverage(input: {unitNumber: "370"}) { gaps machines { machine { id } ingredients { item feedingArms covered } } } } }

Validated: gaps is the list of ingredients with no feed path (empty means fully covered; unit 370 returned [] when checked). Topology only, not stock.

areaGraph: everything in an XY box and how it connects

10 · Invariants

  • Wiring is not throughput. No rate or item count lives on a wiring edge. A packed static belt reads zero flow with full lanes.
  • Fluid, wire and rail edges are undirected in meaning. Match them without an arrow.
  • Unknown link kinds fail the export. Silent skips would make contract drift look like a smaller factory.
  • Snapshots replace scopes. A partial or older snapshot never patches a newer world.
  • Ticks are per read. Each node carries the tick of the leaf that owned it; a multi-leaf snapshot spans ticks and says so in the manifest.
  • Inline and mod Lua are one text. TestTopologyModPreludeParity fails when the graph_prelude, graph_leaf or graph_mobile regions of topology.lua drift from the Go fallback.
  • The graph is a snapshot, not live state. Refresh with just graph-sync or the GraphQL mutation exportMapSnapshotToMemgraph; read with the read-only memgraph { query } field. Each Entity carries the tick and snapshot id it was exported at.
